# 38 — How exact is the mirror?

Of 728 PostgreSQL statements run unchanged against the mirror through DuckDB,
**171 (23.5%) return exactly what PostgreSQL returns** — same column names, same
types, same values, same order.

**127 (17.4%) return a different value without an error**, and 97 (13.3%) fail on
the mirror while PostgreSQL answers.

The rest — 308 statements, 42.3% — return the same values under a different type,
and two thirds of those (208) differ only in that an `integer` came back as a
`bigint`. Count those as fine and the mirror agrees on **379 of 728 (52.1%)**.

Everything here comes from
[`bench/exactness/results/results.json`](../bench/exactness/results/results.json),
written by [`bench/exactness/run.py`](../bench/exactness/run.py); the per-statement
tables are in the generated
[`REPORT.md`](../bench/exactness/results/REPORT.md) beside it. One command rebuilds
all of it from an empty directory:

```
sudo python3 bench/exactness/run.py
```

---

## Why this had to be measured

Every earlier document measures whether the mirror holds the same **rows** as the
source. `qs-verify` answers that, and it answers it well. It says nothing about
whether a **query** over those rows gives the same answer, and that is the only
thing a user of the mirror ever sees.

The gap is not hypothetical. The mirror stores every integer as BIGINT, an
unconstrained `numeric` as DECIMAL(38,9), and uuid, json, jsonb, arrays, bytea,
enums, inet and interval as VARCHAR. DuckDB then applies its own dialect on top. A
competitor measured plain DuckDB at 23% agreement with PostgreSQL over 8,323
statements, wrong-not-refused on about 15%. This project had no number at all.

It has one now, and it is about the same.

## The measurement

**Source.** PostgreSQL 17.12, database collation ICU `en-US`. Six tables, 10,345
rows, generated by arithmetic on `generate_series` — no `random()`, no `now()` —
covering every commonly used type with NULLs in every column: the integer widths,
numeric constrained, scale-0 and unconstrained, real and double including NaN, −0,
`5e-324` and the float4 extremes, text with mixed case, accents, CJK, an emoji,
trailing spaces and empty strings, `char(8)`, uuid, date/time/timestamp/timestamptz
including both US DST boundaries of 2024, `±infinity`, year 1 and year 9999,
interval, timetz, json, jsonb, bytea, three array types, an enum whose order is not
alphabetical, and inet.

**Mirror.** Built by the production sidecar on a standby, as the plugin deploys it.
The bulk rows arrive by snapshot; the tricky rows are inserted afterwards and
arrive over the replication stream, so both write paths are measured. Nothing is
compared until `qs-verify` says MATCH on all six tables.

**Reader.** Python `duckdb` 2.0.1 over views made from `qs-query -view`, with the
one setting `qs-query` recommends (`default_null_order =
'NULLS_LAST_ON_ASC_FIRST_ON_DESC'`). Both sessions run in `America/New_York`: a
comparison in UTC cannot see a single daylight-saving difference.

**Corpus.** 728 `SELECT` statements in fourteen files under
[`bench/exactness/corpus/`](../bench/exactness/corpus/), each with an id. They are
ordinary PostgreSQL — `::` casts, `->>`, `ILIKE`, `to_char`, `string_agg(... ORDER
BY)`, `DISTINCT ON`, `FILTER`, `NOT IN` over a nullable subquery — written as
someone would write them against PostgreSQL, not adjusted to suit DuckDB.

**Comparison.** PostgreSQL's values are fetched as the text the server sent, with
no client adaptation. DuckDB's are read through Arrow and rendered the way
PostgreSQL would print the same value. Column count, names, values and types are
compared separately; row order is compared when the outermost query has an ORDER
BY and as a multiset when it does not. Two float8 results within a relative 1e-12
are the same answer (two statements needed that). Each statement lands in one
class:

| outcome | statements | share |
|---|---:|---:|
| exact | 171 | 23.5% |
| same values, different column name | 2 | 0.3% |
| same values, different type | 308 | 42.3% |
|   — of which only the integer width differs | 208 | 28.6% |
| **different value** | **127** | **17.4%** |
| error on mirror only | 97 | 13.3% |
| error on source only | 9 | 1.2% |
| error on both | 14 | 1.9% |

### The comparison is itself tested

A harness that renders one engine's values in another's format can be wrong in
either direction, so `run.py` checks itself on every run and exits non-zero if
any of this fails:

- the corpus against **PostgreSQL itself** must be 100% exact: 705 exact and 23
  identical errors of 728;
- 28 **deliberately wrong pairs** must each be flagged as the right class — a
  trailing space, `''` against NULL, `1.50` against `1.5`, a reversed ORDER BY, one
  duplicate too many, `1 month` against `30 days`;
- 22 **literal pairs** that both engines parse must render identically, which is
  what tests the DuckDB-to-PostgreSQL renderer rather than assuming it.

The third check caught a float4 formatting crash before the first result existed.
It did not catch the bug that mattered, which is the next section.

## An artefact that hid a real bug

The first complete run showed bare `SELECT d FROM t_time` as matching. It does not.

The mirror writes `-infinity` as the smallest integer — INT32_MIN for a date,
INT64_MIN for a timestamp — because that is how PostgreSQL stores it. **DuckDB's
`-infinity` is one above that.** So DuckDB reads the mirror's `-infinity` as an
ordinary, finite date:

```
postgres   -infinity
mirror     5877642-06-23 (BC)                    date
mirror     290309-12-21 (BC) 19:59:05.224192     timestamp
```

My renderer treated anything at or below DuckDB's sentinel as `-infinity`, and so
rendered the absurd date back into the right answer. It was found only because
`d::text` — where DuckDB does the rendering — disagreed while bare `d` did not.
The renderer now recognises exactly DuckDB's two sentinels and nothing near them,
and six statements moved from matching to wrong. Eleven are wrong for this reason
in all, among them `isfinite(ts)` returning true and `WHERE ts = '-infinity'`
missing its row. `+infinity` is
unaffected: the two engines agree on that one.

That is one harness artefact found by hand, and it ran in the direction that
flatters the mirror. After the fix I checked 42 of the 127 different-value
statements outside the harness — `psql` on one side, DuckDB's own `fetchall()` on
the other, no shared code — and **all 42 were real differences; none was an
artefact of rendering.**

Three things in that table are worth reading twice.

**Half of all comparison-and-ordering statements are wrong**, and so are 10 of 36
LIMIT statements. With LIMIT the sort key decides *which* rows come back, so a
collation difference there is not a presentation problem.

**Joins and subqueries are fine**: 37 of 48 exact, and all three NULL-semantics
traps (`NOT IN` over a nullable subquery, `> ALL`, `NOT EXISTS`) agree.

**JSON does not work**: 34 of 54 fail outright. They fail loudly, which is the
better way to fail.

## Root causes

Attribution here is by experiment, not by reading the SQL. Every statement also
runs on a **typed control**: the same DuckDB with the same settings, over tables
that keep the source's own column types, copied in with DuckDB's postgres
scanner. If the control is exact and the mirror is not, the mirror's type mapping
is the whole cause. If the control fails the same way, faithful types would not
have helped.

The control is exact on **411 of 728 (56.5%)** and wrong on 108. So the mirror's
type mapping costs 240 exact answers, and 24 of the mirror's 127 wrong values are
exact on the control. The rest are wrong on the control too: DuckDB, not the
mapping.

The 127 wrong values were then each assigned a mechanism by reading both results
([`root_causes.tsv`](../bench/exactness/root_causes.tsv)). Ranked by how many
statements each group explains, across all 543 that diverge:

| group | statements | wrong value | error on mirror | same values, other type |
|---|---:|---:|---:|---:|
| the mirror's type mapping and storage | 256 | 39 | 11 | 206 |
| DuckDB semantics | 170 | 51 | 8 | 102 |
| function or syntax missing in DuckDB | 78 | 0 | 78 | 0 |
| ordering and collation | 35 | 35 | 0 | 0 |
| column naming, session identity | 4 | 2 | 0 | 2 |

(The "DuckDB semantics" row includes the 9 statements where PostgreSQL raises and
DuckDB answers.)

### 1. Collation — 35 wrong values, the largest single cause

DuckDB compares text by code point. PostgreSQL uses the database collation.

```
SELECT 'a' < 'B'                             postgres t      mirror f
SELECT least('apple','Banana','cherry')      postgres apple  mirror Banana
SELECT count(*) FROM t_str WHERE t < 'b'     postgres 670    mirror 809
SELECT name FROM customers ORDER BY name     240 of 300 rows in a different position
```

This is the one cause that depends on how the source was created, so it was
measured both ways. CloudNativePG's default is the **C** locale, and on a
C-locale source these statements agree:

| source collation | exact | different value | of the 35 collation statements, still wrong |
|---|---:|---:|---:|
| ICU `en-US` (the headline) | 171 (23.5%) | 127 (17.4%) | 35 |
| `C` | 193 (26.5%) | 99 (13.6%) | 3 |

The C-locale run is in
[`results/locale-C/`](../bench/exactness/results/locale-C/REPORT.md)
(`run.py --locale C`). It is not a free win. Six statements that agree under
`en-US` become wrong under `C`; I did not hand-check those six, but every one
applies `ILIKE`, `upper()` or `lower()` to non-ASCII text, where a C-locale
PostgreSQL and DuckDB part ways in the other direction.

### 2. Type mapping that changes values — 39 wrong values

These are the ones the project owns outright.

**`-infinity` is not `-infinity` (11).** Above. One sentinel value off.

**`char(n)` loses its padding, but only sometimes (9).** The snapshot reads every
column as `col::text`, and that cast strips a `bpchar`'s padding. The replication
stream sends the padded form. So the same value is stored two ways depending on
when the row was written:

```
char(8) 'ab'      postgres 'ab      '    snapshot row 'ab'    stream row 'ab      '
```

`qs-verify` reports the streamed form as DIVERGED. Either way the column is a
VARCHAR, so PostgreSQL's rule that `ch = 'ab'` ignores trailing spaces is gone:
`WHERE ch = 'ab      '` finds 41 rows in PostgreSQL and none in the mirror.

**`inet` gains a `/32`, by the same mechanism (3).** `'192.168.1.7'::inet::text`
is `192.168.1.7/32`. Snapshot rows carry the suffix, streamed rows do not, and
`qs-verify` says DIVERGED on the streamed ones.

**An enum sorts alphabetically (8).** `ORDER BY mood` returns `ecstatic, happy,
ok, sad` where PostgreSQL returns `sad, ok, happy, ecstatic`. `min(e)` is
`ecstatic` instead of `sad`.

**`real` is stored as DOUBLE (4).** `0.1::real` widened to float8 is
`0.10000000149011612` in PostgreSQL; the mirror parsed the text `0.1` and holds
`0.1`. More precise, and a different answer: `avg(r)` differs in the ninth digit
and `WHERE r = 0.1::real` returns no row.

**A filter for NaN returns nothing (1).** `WHERE d = 'NaN'` finds the row in
PostgreSQL and none in the mirror. The value is there — `SELECT d` shows it —
but Parquet min/max statistics exclude NaN and DuckDB prunes on them; disabling
`filter_pushdown` and `statistics_propagation` brings the row back.

The remaining three: a uuid compared against an upper-case literal matches nothing
(VARCHAR comparison is case-sensitive), an interval sorts as text, and an
unconstrained numeric cast to text shows nine decimals (`60695.300000000`).

### 3. DuckDB semantics — 51 wrong values

No type mapping fixes these; the control gets them wrong too.

| what | PostgreSQL | DuckDB | statements |
|---|---|---|---:|
| `7 / 2` | `3` | `3.5` | 9 |
| `0.1::real * 3` | `0.30000000447034836` | `0.30000001192092896` | 5 |
| `pg_typeof(1.5)` | `numeric` | `decimal(2,1)` | 5 |
| `lower('İstanbul') = 'istanbul'` | false | true | 4 |
| `LIKE 'a\_b%'` (backslash escape) | 34 rows | 0 rows | 3 |
| `tz - tz` across a DST change | `71 days 11:47:00` | `71 days 12:47:00` | 3 |
| `'éclair-1' ~ '^\w+-\d+$'` | true | false | 2 |
| `SIMILAR TO '(apple\|banana)%'` | 75 rows | 0 rows | 2 |
| `upper('straße')` | `STRASSE` | `STRAẞE` | 2 |
| `extract(second FROM ts)` | `35.005005` | `35` | 2 |
| `round(d::numeric, 2)` on `-4510.1649…` | `-4510.16` | `-4510.17` | 2 |
| `e > 'ok'` on an enum | enum order | text order | 2 |
| `round(0.5::float8)` | `0` | `1` | 1 |
| `substring('hello' FROM -1 FOR 4)` | `he` | `o` | 1 |
| `SELECT generate_series(1, 5)` | 5 rows | 1 row holding a list | 1 |
| `j -> 'a'` where `j` is `{"a":1,"a":2}` | `2` | `1` | 1 |
| `'abcdef'::varchar(3)` | `abc` | `abcdef` | 1 |

Five more one-offs (float-to-text layout, `concat()` of a boolean, a time literal
past the microsecond, `->>` re-rendering `2.50` as `2.5`) are in `REPORT.md`.

The DST row deserves a sentence, because it is the one I did not expect:
subtracting two `timestamptz` values that straddle a clock change gives an
interval one hour longer than the elapsed time. `extract(epoch FROM ...)` of it is
3600 seconds off.

Integer division is the only one with a switch. `SET integer_division = true`
moves all nine from wrong to right, and turns division by zero back into an error
on both sides.

### 4. Missing in DuckDB — 78 errors

`to_char` alone is eight of them. Then: `initcap`, `btrim`, `to_date`,
`make_interval`, `date_bin`, `justify_days`, `width_bucket`, `div`, `every`,
`regexp_match`, `quote_literal`, `num_nulls`, `array_upper`, the whole `jsonb_*`
family, the operators `#`, `#>`, `#>>`, `?`, `?|`, `@?`, `|/`, the syntax
`OVERLAPS` and `FETCH FIRST ... WITH TIES`, the `\m` regex escape, and
`octet_length` and `encode` on text. Another 8 errors, counted under DuckDB
semantics above, are inputs DuckDB will not cast: `'on'::boolean`,
`'20240229'::date`, `'1-2'::interval`.

### 5. Type mapping that only breaks the statement — 11 errors

Arrays and intervals are VARCHAR, so `3 = ANY (ia)`, `ia @> ARRAY[1,2]`,
`unnest(ia)`, `ts + iv` and `iv * 2` do not bind: ten statements. The eleventh is
`chr(65 + id % 26)`, which has no BIGINT overload. All eleven run on the typed
control.

## Values the mirror will not hold

Each of these was mirrored alone, one value in one table
([`probes.sql`](../bench/exactness/probes.sql), results in
[`probes.json`](../bench/exactness/results/probes.json)). None is in the measured
tables.

| type | value | what happened |
|---|---|---|
| `numeric` | `NaN`, `Infinity` | mirror halts |
| `numeric` | `0.123456789012345` (15 decimals) | mirror halts |
| `numeric` | `1::numeric / 3` | mirror halts |
| `numeric` | a 30-digit integer | mirror halts |
| `numeric(50,2)` | `1.50` | **the sidecar panics** (`slice bounds out of range`) |
| `date`, `timestamp` | `0044-03-15 BC` | mirror halts |
| `timestamptz` | `0001-01-01 00:00:00+14` | mirror halts |
| `timestamp` | `294276-12-31` | mirror halts |
| `date` | `5874897-12-31` | mirror halts |
| `double precision` | `1000000`, `123456789.12345679`, `Infinity` | mirrored correctly; **`qs-verify` says DIVERGED** |
| `real` | `-Infinity` | mirrored correctly; `qs-verify` says DIVERGED |
| `char(8)` | `ab` | snapshot and stream store it differently; `qs-verify` says DIVERGED |
| `inet` | `192.168.1.7` | snapshot and stream store it differently; `qs-verify` says DIVERGED |

The halts are documented behaviour and each names its value. Three rows are not.

`numeric(50,2)` holding `1.50` crashes the process rather than halting it. The
value fits in DECIMAL(38,9) many times over; it is the declared precision the
writer cannot take.

`qs-verify` reports a float8 of exactly one million as a divergence. DuckDB reads
`1000000` back from both rows, so the mirror is right and the verifier is wrong.
The measured tables avoid the values that trip it for one reason only: this suite
does not compare anything until `qs-verify` says MATCH.

And `char(n)` and `inet` are stored differently by the two write paths, which is
a mirror that disagrees with itself. The measured tables load those rows by
snapshot for the same reason.

## What the project can remove, and what it cannot

**By mapping a type differently.** These need no change to anyone's query.

| change | removes |
|---|---|
| keep `smallint` and `integer` as INT16 / INT32 | 180 type-only differences, and 4 statements where PostgreSQL overflows and the mirror does not |
| write `-infinity` as DuckDB's sentinel | 11 wrong values |
| snapshot `char(n)` and `inet` in their output form, not `::text` | the two paths agree; 3 wrong inet values. `char(n)` comparison semantics stay lost |
| store `real` as FLOAT | 4 wrong values. 5 other float4 differences are DuckDB's and stay |
| store enums as a DuckDB ENUM | 7 of the 8 wrong orderings (the control gets those right). `e > 'literal'` stays wrong |
| store arrays as lists, `interval` as INTERVAL, `uuid` as UUID | 10 errors, 2 wrong values |
| refuse `numeric(p > 38)` | a panic becomes a halt |

**By a setting `qs-query` already has a place for.** `SET integer_division =
true` belongs beside the NULL-order setting: 9 wrong values. Nothing else in the
list has a switch.

**By a rewrite layer.** `to_char`, `initcap`, `btrim`, `to_date`, the `jsonb_*`
functions, `#>>`, `?`, the LIKE default escape, `SIMILAR TO` and
`generate_series` in the SELECT list are translations rather than semantics: the
78 errors and 6 of the wrong values. That is the size of the job a compatibility
layer takes on — see the caveat below about pg_duckdb.

**Only by changing the query, or the source.** Collation is 35 wrong values and
there is no type to map. A source created with the C locale (CloudNativePG's
default) loses 32 of them and gains the 6 above. DuckDB has ICU collations of its
own; whether `SET default_collation` reproduces PostgreSQL's `en-US` order was
**not measured here**. Unicode case folding, ASCII-only regex classes,
half-away-from-zero rounding and `timestamptz` subtraction across DST are
DuckDB's own.

## What this does not cover

- **It reads through Python `duckdb`, not pg_duckdb.** The deployed path puts
  PostgreSQL's parser in front of DuckDB and may translate some of what fails
  here. Nothing in this document measures that path: the 78 missing-function
  errors in particular should not be read as its number. The wrong values that come from stored data — `-infinity`,
  `char(n)`, `inet`, enum order, NaN — do not depend on the reader.
- **728 statements written by one author** are a sample, not a census. The
  category shares are the corpus's shape, not anyone's workload; a workload that
  never orders by text and never divides integers will do much better than 23.5%.
- **`SELECT` only.** No DML, no DDL, no prepared-statement parameter typing.
- **A caught-up mirror.** Freshness, compaction landing mid-query and DDL
  barriers are other documents' subject; this is the answer once the rows are
  there.
- **The typed control is not perfectly faithful.** The postgres scanner reads an
  unconstrained `numeric` as DOUBLE and `char(n)` and `inet` as VARCHAR, so for
  those three the control cannot separate the mapping from the engine, and their
  causes were assigned by hand.
- **One version of each engine**, one time zone, two locales.
